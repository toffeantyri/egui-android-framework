# 📋 Протокол оценки задачи (TDD + Regression)

## Шаг 1. ЗАЧЕМ

**Пользователь продукта:**
- Какую проблему решает?
- Что он получит в итоге?

**Разработчик фреймворка:**
- Какую боль снимает?
- Что станет проще/надёжнее?

> ⚠️ Если не можешь сформулировать оба — остановись и уточни.

## Шаг 2. ЧТО

**Задача:** <одно предложение>

**Критерии успеха:**
- [ ] ...

**Границы (НЕ делаем):**
- ❌ ...

## Шаг 3. ПОВЕДЕНИЕ

### Ожидаемое (happy path)
- При корректных входных данных → ...
- При типичном сценарии → ...
- При валидном API-вызове → ...

### Не ожидаемое (edge cases, ошибки, инварианты)
- При невалидных данных → ошибка/panic/fallback
- При нарушении инварианта → ...
- Что НЕ должно происходить (deadlock, двойной вызов, утечка)
- Граничные условия (0, MAX, пустой список, null)
- Какие invariant'ы ломаются при баге

### Из реальных багов (regression-источник)
- Баги, найденные на устройстве при ручном тестировании
- Логи/стейты, достаточные для воспроизведения
- Edge cases, не очевидные из спецификации

> 💡 Каждый найденный баг = тест, который ДОЛЖЕН быть написан.
> Без теста фикс бага запрещён.

## Шаг 4. ПЛАН (TDD-цикл)

Каждый шаг помечен фазой:
- 🅰️ **[АБСТРАКЦИЯ]** — типы, трейты, сигнатуры (без тела)
- 🔴 **[RED]** — тесты на поведение из Шага 3 (они ПАДАЮТ)
- 🔴 **[RED-regression]** — тест, воспроизводящий реальный баг
  (пишется ДО фикса, должен ПАДАТЬ на текущем коде)
- 🟢 **[GREEN]** — минимальная реализация, тесты проходят
- 🔧 **[REFACTOR]** — улучшение (только при зелёных тестах)

**Порядок:** инвазивные изменения (API, 5+ файлов) → локальные.
Если в середине появилось инвазивное — стоп, переупорядочи.

## Шаг 5. ТЕСТЫ

- **Юнит-тесты:** чистые функции, reducer'ы, утилиты
- **Интеграционные:** Component ↔ StateStore ↔ Dispatcher,
  ChildStack push/pop с lifecycle
- **Regression-тесты:** воспроизводят баги, найденные на устройстве.
  Пишутся ПОСЛЕ обнаружения бага, но ДО фикса.
  Остаются навсегда как гарант от повторного появления.
- **Моки:** `egui::Context` через `__run_test_ui`,
  реальные каналы (не моки), мок `AndroidBackend`

## Шаг 6. Формат ответа

📋 Оценка задачи

**Зачем:**
- Пользователь: ...
- Разработчик: ...

**Задача:** ...

**Критерии:**
- [ ] ...

**Границы:**
- ❌ ...

**Поведение:**
- ✅ Ожидаемое: ...
- ❌ Не ожидаемое: ...
- 🐛 Из реальных багов: ...

**План (TDD):**
| # | Фаза | Шаг | Инвазивность | Тесты |
|---|------|-----|--------------|-------|
| 1 | 🅰️ АБСТРАКЦИЯ | Определить трейт X | 🔴 | — |
| 2 | 🔴 RED | Тесты happy path + edge cases | 🔴 | 5 тестов |
| 3 | 🔴 RED-regression | Воспроизвести баг #42 | 🟡 | 1 тест |
| 4 | 🟢 GREEN | Реализация X + фикс бага | 🔴 | проходят |
| 5 | 🔧 REFACTOR | Упростить Y | 🟡 | проходят |

Подтверждаете план?

## Красные флаги (стоп → вопрос)

- 🚩 Хочется переделать что-то «заодно»
- 🚩 Идея «лучшего» решения без обсуждения
- 🚩 Задача разрастается за границы
- 🚩 Неясно, как покрыть тестами
- 🚩 Шаг без фазы TDD (АБСТРАКЦИЯ/RED/GREEN/REFACTOR)
- 🚩 **Нашёл баг на устройстве → сначала тест, потом фикс**
- 🚩 **Фикс бага без regression-теста запрещён**
